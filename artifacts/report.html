5 · Baseline comparison — Loki vs. Garak & Promptfoo

ToolStatusFindingsNotes
Garak 0.16.0 (NVIDIA)ran 4Ran dan.Dan_11_0 + latentinjection.LatentInjectionFactSnippetEiffel (258 probe requests). Under Loki's canary oracle, 4/256 (1.6%) of its latent-injection requests actually leaked the tier-1 canary; garak's own generic detectors reported the target as resilient and did not flag those leaks. Garak 0.16 DOES include latentinjection, agent_breaker and sysprompt_extraction probe families (its catalog has grown), so it is not blind to indirect injection — but it replays a fixed prompt set and does not adapt.
Promptfoo (latest, npx)ran 0Ran 5 representative single-turn injection prompts (override, authority, roleplay, base64, DoS) against tier-1. 0/5 leaked the canary — the static plaintext variants were caught by tier-1's denylist, exactly the case where a non-adaptive replay stalls.

What Loki found that they did not: On the SAME tier-1 target, Loki's adaptive genetic search reached ~41% attack success (matrix phase) vs. garak's 1.6% and promptfoo's 0% under an identical oracle — because it evolves payloads and routes on refusal patterns instead of replaying a fixed list. Loki also produces artifacts neither baseline does: per-finding N-trial reproduction with Wilson 95% CIs, de-duplication to DISTINCT findings (not raw hit counts), a deterministic `loki replay ` for every reported finding, deterministic tripwire proofs of agent excessive-agency (delete_records / non-allowlisted email) on a sandboxed tool-using agent, and the guardrail-tier vs. technique-family effectiveness matrix.

What they found that Loki did not: Honestly: garak ships a far broader catalog of probe CATEGORIES than Loki's five OWASP classes (toxicity, malware generation, package hallucination, glitch tokens, encoding smuggling, visual jailbreak, data-leak replay, and more) plus mature, well-tuned detectors; promptfoo has a polished red-team grader ecosystem and first-class CI integration. Loki is deliberately narrower in surface but deeper on adaptivity and evidence-grade, reproducible proof.

8 · Limitations

  • The primary targets pair a documented, seeded LLM *simulator* with REAL guardrail code (denylist, input classifier, delimiter isolation, output filter) and real tripwires. Headline rates therefore measure the guardrail stack's behavior under a modeled model; they are not a claim about any specific commercial LLM. The same attacks run unchanged against a real local HF model via the --backend hf option.
  • The trained classifier is a judge *signal*, not ground truth; the canary/tripwire oracle is authoritative for self-built targets. Where no oracle applies, success depends on classifier + LLM-judge agreement, which is weaker.
  • HackAPrompt 1.0 became a gated Hub dataset (requires HF authentication). The classifier was trained on a public, ungated prompt-injection corpus instead; the exact dataset is named in §6. Its labels denote injection *attempts*, not success.
  • Without an API key, the LLM-as-judge runs its fixed rubric in deterministic rule-based mode rather than as a large model. Set OPENAI_API_KEY to enable the model-backed judge; the rubric is identical.
  • Out of scope (not reliably black-box testable): training-data poisoning, supply-chain, model theft, overreliance.
  • Reproduction CIs are wide at n=10 by design; raise --reproduction-trials for tighter intervals at higher budget cost.
